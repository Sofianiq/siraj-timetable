# بنية النظام والتقنيات المستخدمة

## نظرة عامة

```
 المتصفح (حاسوب / لوحي / هاتف)                         السحابة (مجاني)
┌────────────────────────────────────────┐          ┌──────────────────────────┐
│ GitHub Pages: ملفات ثابتة HTML/CSS/JS  │          │ Firebase Authentication  │
│                                        │  HTTPS   │ (الحسابات والدخول)       │
│  واجهات (views) ─┐                     │ ───────▶ ├──────────────────────────┤
│  محرك التعارضات ─┼─▶ طبقة البيانات    │ ◀─────── │ Cloud Firestore           │
│  مولّد الجداول  ─┘    (store.js)       │ مزامنة   │ (قاعدة البيانات + قواعد   │
│  التصدير PDF/Excel                     │  فورية   │  الأمان والصلاحيات)       │
└────────────────────────────────────────┘          └──────────────────────────┘
```

- **لا يوجد خادم خاص** ولا خطوة بناء (Build). الملفات تُرفع كما هي على GitHub Pages، فيسهل النشر والصيانة لغير المتخصص.
- **Firestore** يوفّر المزامنة الفورية عبر `onSnapshot`. أي تعديل يصل إلى كل الأجهزة المفتوحة خلال أقل من ثانية.
- **التخزين المؤقت المحلي** (`persistentLocalCache`) يجعل الفتح سريعاً، ويسمح بالعمل عند انقطاع الإنترنت، ثم تُرفع التعديلات عند عودة الاتصال.
- **الوضع التجريبي المحلي**: إذا لم تُملأ إعدادات Firebase تُخزَّن البيانات في `localStorage`، فيمكن تجربة النظام فوراً.
- **Supabase (بديل Firebase):** إذا مُلئ `supabaseConfig` في `js/config.js` يعمل النظام على Supabase، وله الأولوية على Firebase. الواجهات لا تعرف أي قاعدة تُستخدم، فطبقة `store.js` تقدّم الدوال نفسها للأوضاع الثلاثة. التفاصيل في قسم «Supabase» أدناه.

## التقنيات

| المجال | التقنية | السبب |
|---|---|---|
| الواجهة | HTML + CSS + JavaScript (ES Modules) بدون أطر عمل | بلا اعتماديات وبلا بناء، وسريع، وسهل التعديل |
| الخط | Tajawal (Google Fonts) | خط عربي واضح للشاشة والطباعة |
| قاعدة البيانات | Google Cloud Firestore، أو Supabase (PostgreSQL) | مجانية للاستخدام المعتاد، ومزامنة فورية، وقواعد أمان |
| الحسابات | Firebase Authentication (بريد وكلمة مرور) | مجانية، وتدعم استعادة كلمة المرور |
| Excel | ExcelJS (يُحمَّل عند الحاجة فقط) | تنسيق كامل: دمج خلايا، وألوان، واتجاه RTL، وإعدادات الطباعة |
| PDF | html2canvas + jsPDF (يُحمَّلان عند الحاجة) | يحافظ على العربية والتنسيق كما يظهر في الطباعة بالضبط |
| السحب والإفلات | Pointer Events (مكتوب داخل النظام) | يعمل بالفأرة واللمس دون مكتبات |
| الاستضافة | GitHub Pages | مجانية ومع HTTPS |
| الاختبارات | `node --test` | اختبارات لمحرك التعارضات والمولّد |

### عدة كليات
- كل قسم ينتمي إلى كلية (`collegeId`)، والمراحل والشعب والمواد والمحاضرات تنتمي إلى قسم؛ لذا تُعرف كلية أي عنصر من قسمه.
- **المشترك:** الأساتذة (`deptId` قسم أساسي للتنظيم فقط) والقاعات (`collegeId` الكلية المالكة للتنظيم وأولوية التوليد). محرك التعارضات يفحص كل محاضرات الجامعة بلا تمييز بين الكليات.
- **الخاص:** المواد. المحرر والمولّد يعرضان مواد القسم/الكلية المختارة فقط (وللفصل الحالي ومرحلة الشعبة، مع خيار عرض الكل).
- اختيار الكلية في الشريط العلوي يُحفظ في متصفح المستخدم (`localStorage`) ويُطبَّق على كل الصفحات.
- **ترقية البيانات:** عند أول دخول لمدير النظام بعد التحديث تُرقّى البيانات القديمة مرة واحدة، ثم تُرفع `schemaVersion` حتى لا تتكرر العملية (`migrationPlan` في `js/seed/radiology.js`):
  - **الإصدار 2:** تُضاف كليتا الصيدلة وطب الأسنان.
  - **الإصدار 4:** كلية الصيدلة أو طب الأسنان المُدارة بلا أقسام يُنشأ لها «قسم عام» بمراحله وشعبه.
  - **الإصدار 3:** إن كانت الكلية مسجّلة سابقاً كـ«جهة خارجية» بالاسم نفسه تُحوَّل إلى كلية مُدارة، وتُدمج النسخ المكررة (مثل «الاسنان» و«الأسنان»). كذلك تُنشأ شعبة «صباحي» لكل مرحلة ليس لها شعب، وتُربط كل محاضرة بلا شعبة بشعبة مرحلة مادتها إن كانت للمرحلة شعبة واحدة.
  - **الإصدار 5:** الدوام والجدول المطبوع من 8:30 إلى 2:30 (`WORK_HOURS`)، وتحويل القاعات التي يبدأ اسمها بـ«مختبر» إلى نوع مختبر، واستيراد المناهج الرسمية والكادر (`curriculumImportPlan`). كل تعديلات الإعدادات تُجمع في عملية واحدة.
- **المحاضرات بلا شعبة:** المحرر يشترط اختيار شعبة. ما بقي من بيانات قديمة بلا شعبة يظهر ويُطبع في جدول خاص لكل مرحلة (نوع العرض الداخلي `loose`، ومعرّفه «القسم|المرحلة»)، حتى لا يختفي من التصدير.

تخزين الوقت بالدقائق (وليس بحصص ثابتة) هو ما يسمح **بالتعديل الحر لوقت المحاضرة**، مثل 8:45 إلى 10:15. ولكل محاضرة **مصفوفة شعب**، فتُمثَّل المحاضرة المشتركة لعدة شعب، ويُكشف تعارضها مع أي شعبة منها.

## محرك التعارضات (`js/conflicts.js`)

تتعارض محاضرتان إذا كانتا في الفصل نفسه واليوم نفسه، وتداخل وقتاهما: `a.start < b.end && b.start < a.end`. وعندها يفحص المحرك:

- **أخطاء** (تمنع الحفظ):
  - الأستاذ نفسه في المحاضرتين.
  - القاعة نفسها، ويشمل ذلك كل أقسام الكلية وحجوزات الكليات الأخرى.
  - شعبة مشتركة بين المحاضرتين.
- **تنبيهات**:
  - مجموع طلبة الشعب أكبر من سعة القاعة.
  - وقت المحاضرة خارج أوقات توفر الأستاذ.
  - المحاضرة خارج وقت الدوام الصباحي أو المسائي للشعبة.
  - محاضرة عملية في قاعة ليست مختبراً، أو نوع المختبر غير مطابق.

يُستدعى المحرك:
- أثناء السحب، لتلوين الموقع المقترح.
- في نافذة التحرير، لحظة بلحظة.
- قبل كل حفظ.
- عند اعتماد نتيجة التوليد، للتأكد من أن مستخدماً آخر لم يغيّر البيانات في الأثناء.

ويُجمَّع الفحص الشامل حسب (الفصل، اليوم) لتسريعه.

## خوارزمية التوليد التلقائي (`js/generator.js`)

1. **تحويل المواد إلى طلبات:**
   - الساعات تُقسَّم إلى كتل متوازنة، مثل 3 ساعات → 2 + 1.
   - النظري يُجمع لكل شعب المرحلة في نوع الدراسة نفسه، ويمكن تعطيل ذلك لكل مادة.
   - العملي يكون لكل شعبة على حدة.
   - تُطرح الساعات المغطاة بمحاضرات ثابتة (يدوية أو مثبتة).
2. **الترتيب حسب الصعوبة** (Most-Constrained-First): الطلب ذو الخيارات الأقل أولاً، ثم الأطول، ثم الأكثر طلبة.
3. **الاختيار بالكلفة الأقل** من بين كل الخيارات الصالحة (يوم × وقت × قاعة)، التي تحقق القيود الصارمة كلها. وتشمل الكلفة:
   - تكرار المادة في اليوم نفسه.
   - الفراغات بين المحاضرات.
   - تجاوز الحمل اليومي للشعبة أو الأستاذ.
   - هدر سعة القاعة.
   - عدم ملاءمة القاعة أو المختبر.
   - تفضيل خفيف للبدايات المبكرة.
4. **الإصلاح** (Repair): إن لم يجد الطلب مكاناً، يحاول المولّد إزاحة طلب واحد يعيقه وإعادة وضعه في مكان آخر.
5. **إعادة المحاولة العشوائية** (Random Restarts): حتى 30 محاولة بترتيبات مختلفة، ضمن ميزانية زمنية تقارب 2.5 ثانية، ثم تُختار النتيجة الأفضل (أقل عدد غير مُجدول، ثم أقل كلفة).

القيود الصارمة التي يحترمها المولّد:
- كل المحاضرات الموجودة في الجامعة، من كل الأقسام والحجوزات الخارجية.
- أوقات توفر الأستاذ.
- وقت الدوام الصباحي أو المسائي.
- العملي في المختبرات فقط.

## الأمان والصلاحيات

- القواعد في `firestore.rules` تُطبَّق **على الخادم**، فلا يمكن تجاوزها من المتصفح.
- القراءة عامة، ليتمكن الطلبة من فتح رابط العرض بدون حساب.
- الكتابة حسب الدور:
  - مدير النظام: كل شيء.
  - معاون العميد: المستندات التي ينتمي قسمها (`deptId`) إلى كليته، والأقسام والقاعات التي `collegeId` فيها يساوي كليته.
  - مسؤول القسم: فقط المستندات التي `deptId` فيها يساوي قسمه.
- كتابات غير مدير النظام تُرسل على دفعات صغيرة، لأن القواعد تقرأ ملف المستخدم والقسم عند كل كتابة ولـ Firestore حد لعدد هذه القراءات في الدفعة الواحدة.
- المستخدم الجديد يُنشأ ملفه بصلاحية `viewer` فقط، ولا يرفعها إلا المشرف.

## استيراد المناهج الرسمية (`js/seed/curriculum.js`)

- **المواد:** لكل (قسم، مرحلة، فصل) تُقارن مواد الخطة بالمواد الموجودة بالكلمات بعد توحيد الكتابة وحذف «ال» و«علم». كل كلمة في الاسم الأقصر يجب أن تقابلها كلمة في الأطول، والرقم يجب أن يتطابق، فلا تُطابق «الأطراف العليا» «الأطراف السفلى»، ولا «التشريح 1» «التشريح 2». المطابقة جشعة: الأعلى تشابهاً أولاً، وكل مادة مرة واحدة.
- المادة المطابقة **تُحدَّث** (الاسم الرسمي والساعات والوحدات) فتبقى محاضراتها مرتبطة بمعرّفها، وغير المطابقة **تُضاف**.
- **الأساتذة:** `samePerson` يحذف اللقب (أ.د، م.د، م.م، د.) ويعدّ الاسم المختصر (كلمتان على الأقل) بداية الاسم الكامل شخصاً واحداً، فلا يُضاف أستاذ مكرر.
- العملية آمنة للتكرار: تشغيلها مرة ثانية لا يُنتج أي عملية كتابة.

## Supabase

- **الجداول:** `tt_docs (col, id, data jsonb)` تحمل كل المجموعات بالشكل نفسه الذي في Firestore، و`tt_profiles` لملفات المستخدمين، و`tt_super_admins` لبريد مدير النظام (لا يُقرأ من الموقع).
- **الأمان:** سياسات RLS تطابق `firestore.rules` حرفياً عبر الدالة `tt_can_write(col, data)`. دوال الصلاحية `security definer` حتى لا تدخل في حلقة سياسات.
- **الكتابة الدفعية:** `tt_apply(ops)` تطبّق مجموعة عمليات (set/update/delete) كوحدة واحدة (تنجح كلها أو لا شيء)، وتعمل بصلاحية المستخدم (`security invoker`) فتُطبَّق RLS على كل عملية، وتُرجع خطأ صلاحية بدل التجاهل الصامت.
- **المزامنة الفورية:** Supabase Realtime (`postgres_changes`) على الجدولين، مع `replica identity full` لتصل بيانات الحذف كاملة.
- **النقل من Firebase:** `fetchFirebaseBackup` يقرأ مجموعات Firestore العامة عبر REST (لا يحتاج تسجيل دخول لأن القراءة عامة)، ثم `importAll` يكتبها في Supabase.
- **الاختبار:** `bash supabase/tests/run.sh` يشغّل `schema.sql` على PostgreSQL محلي مع محاكاة لمخطط `auth`، ويختبر كل الأدوار.

## الأداء

- المكتبات الثقيلة (Excel وPDF) لا تُحمَّل إلا عند أول تصدير.
- إعادة الرسم عند وصول تعديل من الآخرين مؤجلة 120 ملّي ثانية ومجمَّعة، ولا تحدث أثناء فتح نافذة تحرير أو أثناء السحب، فلا تضيع مدخلات المستخدم.
- الحدود المجانية لـ Firestore (50 ألف قراءة و20 ألف كتابة يومياً) تكفي كلية كاملة بارتياح.
